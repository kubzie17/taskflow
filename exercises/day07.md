# TaskFlow | Day 7 AWS architecture workshop
**Tuesday 17 November · in person · 09:30–15:30 UK.** Northbridge Repairs wants to move its booking service beyond a developer’s laptop. By 15:25 your team will recommend a pilot and show what must change before a resilient production release. Work in teams of 2, 2 and 3. Rotate the keyboard each challenge. In a pair, one person operates while the other reviews. In the trio rotate cloud operator, network/developer and reviewer. Each learner explains one observation.

2. Check `python -m exercises.day07_lab --help`, `python -m pip show fastapi uvicorn PyJWT` and `python -m pytest -q`. Record the revision and test result. Use Monday's working environment. If it is missing packages, use `python -m pip install -r requirements.txt -r exercises/day05-requirements.txt` in that environment with the class package source. For an unfinished Friday solution you can use historical mode for today's network and storage experiments; record which mode you used.
3. Save a team copy of `exercises/Day_7_Workshop_Workbook.xlsx` **outside your repo**. Share it through your existing private class space or have a nominated scribe enter the team's evidence. Save a personal copy of `exercises/day07-architecture.drawio` outside the repo. In diagrams.net choose **Device → Open Existing Diagram** and open it. With the desktop app use **File → Open**. If unavailable, use PowerPoint shapes or draw a typed sequence of arrows with ports in the workbook. The three diagram tabs are editable.
4. Record only fictional bookings, access decisions, redacted resource descriptions and observed times. Keep passwords, tokens, SSO links, AWS account numbers, principal ARNs, real bucket names, public IPs and customer data out of evidence and Git. The lab uses new stores under `data/day07-lab`. 5. Deliver the completed workbook (or the equivalent Markdown record), labelled diagrams and your network JSON through the usual private class channel. The [Markdown record](day07-evidence.md) mirrors the workbook. Start the matrix during Challenge 1.

## 1 · What can this team actually use? | 20 min
**Scenario.** The sandbox owner has offered access, but nobody has confirmed this role's Region, lifetime, budget or visibility. Establish a route by 10:00. **Tools:** browser, access worksheet; optional already approved AWS CLI. **Start:** owner’s training portal and workbook **1 Access**.
1. Use the supplied sandbox launch link or organisation access portal. Start or resume the assigned lab if that is the provider's normal workflow. Select its assigned role and open **AWS Management Console**. Record whether the session opens, what type of identity you have and how long the provider says it lasts.
2. Read the top-right Region menu. Use **only the Region named by the sandbox owner**. If unspecified, ask the trainer and use the fixture while waiting. IAM is global; EC2/VPC are regional. Record the Region code, approved service list, reset/persistence policy and budget information. Mark unknowns.
3. Split the following lookups. Search **IAM → Roles** (only your role if permitted), **VPC → Your VPCs / Subnets / Route tables / Security groups**, **EC2 → Instances**, **S3 → General purpose buckets**, **CloudWatch → Log groups**, and **Elastic Container Service → Clusters** if approved. Open only the training resource assigned by the owner. Record list success separately from permission to inspect it. An empty list is a result. A visible button does not establish write approval.
4. If approved local CLI is already configured, run `aws sts get-caller-identity --profile COURSE_PROFILE --region APPROVED_REGION --no-cli-pager` with actual settings. Record only the role type and success. Otherwise mark CLI Not tested. Record Available / Denied / Not tested for each operation, with evidence and a follow-up.
5. Choose a provisional route. **A** requires explicit permission, an approved small spend or confirmed coverage and a suitable disposable S3 object location. **B** can read an existing training resource. **C** works offline. In C, use the supplied [fictional inventory](day07-network.json) and [digital observations](day07-evidence.md); label every observation as simulated.
**Done when:** the shared matrix identifies actual access, one constraint and how you know, a route, and an owner for unknowns. Leave unused checks Not tested. **Stretch:** explain a difference between a denied list call and an empty result.

## 2 · Follow one booking to disk | 35 min
**Scenario.** Dispatch can reach a health page. They want evidence that a legitimate booking reaches the right store and that access rules act at the right boundary. **Tools:** VS Code, PowerShell, browser; Docker if ready. **Start:** your repository, three terminals, workbook **2 Evidence**, diagram **Local request**.
1. Terminal 1: `python -m exercises.day07_lab api --mode protected --store primary`. For missing identities, run `python -m exercises.day05_identity` once and invent two different 12+ character passphrases in the hidden prompts. Re-run the service. The existing user should use their original Friday passphrases. If the protected branch cannot start or permit valid writes, tell the reviewer, stop it with Ctrl+C and use `python -m exercises.day07_lab api --mode historical --store primary`. Label all historical observations.
2. Terminal 2: `python -m exercises.day07_lab gateway`. Terminal 3: `python -m exercises.day07_lab point 8071`. Open `http://127.0.0.1:8070/health` in your browser. Compare to `http://127.0.0.1:8071/health`. Capture port, HTTP result and date/time.
3. Run each applicable probe, predicting the outcome before pressing Enter. A denied probe intentionally returns a non-zero shell status. The signed probe obtains a short-lived token privately and prints only the booking response. For historical mode use visitor `call list` and `call book --title "Training trace"`; mark auth evidence Unverified.
```powershell
python -m exercises.day07_lab call list
python -m exercises.day07_lab call list --as reader
python -m exercises.day07_lab call book --as reader --title "Reader probe"
python -m exercises.day07_lab call book --as dispatcher --title "Training trace"
python -m exercises.day07_lab rows --store primary
```
4. Open `exercises/day05_api.py`, `app/database.py` and your `Dockerfile`. Identify the actual factory, where roles are checked and how a successful write reaches a file. Inspect `CMD`, `COPY`, `EXPOSE` and the DB environment setting in the Dockerfile. Where Docker is available, run `docker ps`, then `docker port CONTAINER`, `docker inspect --format '{{json .Config.Cmd}}' CONTAINER` and `docker inspect --format '{{json .Mounts}}' CONTAINER`, replacing CONTAINER with your existing **training** container name. If none exists you can use the [disposable Docker exercise](day07-docker.md). If unavailable, label conclusions from the Dockerfile as configuration-only.
5. Draw the observed browser → entry point → API → storage route, trust boundary, ports, exact SQLite location and where the Docker named volume would mount. Mark the runtime for each finding. Add candidate AWS equivalents for entry, compute, storage and identity.
**Done when:** a peer can follow a single booking ID into SQLite and distinguish the historical image from the protected process. Submit your diagram and two contrasting observations. **Stretch:** demonstrate one direct probe and explain what would enforce that boundary in AWS.

## 3 · Repair the proposed network | 45 min
**Scenario.** Northbridge’s fictional office range is 203.0.113.0/24. Office users need HTTPS to the edge only. Only the edge may forward TCP 8000 to the application. Only the application may use TCP 5432 to a future PostgreSQL service. Internet visitors, unrelated workloads and direct SSH must not gain these permissions. Today's SQLite file uses local file I/O. **Tools:** VS Code, PowerShell, diagram and evidence sheet. **Start:** `exercises/day07-network.json`.
1. Inspect the VPC, six subnets and effective routes. Sketch edge/app/data boundaries across zones A and B. Mark the only default internet route.
2. Make a working copy the first time. On a repeat choose a new name or continue your own copy.
```powershell
Copy-Item .\exercises\day07-network.json .\exercises\day07-team-network.json
python -m exercises.day07_network exercises/day07-team-network.json
```
3. Record the baseline and two surprising flows. Predict one minimal inbound TCP change. Edit only `inbound_tcp` in your working copy. Rules use an integer `port` and either `cidr` or `source_group`. Recognised attached group names include `sg-edge`, `sg-app` and `sg-db`. Re-run after each change; save one intermediate observation.
4. Mark the public entry subnet, two private tiers, responsible identities and traffic direction on your diagram. Route B/A may cross-check VPC → **Subnets → select training subnet → Route table**, then **Security groups → select training group → Inbound rules**. Read settings only. Decide which design principle transfers to the real resource.
**Done when:** your unchanged checker meets its nine client cases, your diagram labels the permitted path, and your reviewer can identify one property the checker does not test. Submit JSON and two before/after flows. **Stretch:** what egress dependencies would a private container need to pull an image and emit logs?

## 4 · Investigate real infrastructure or its local equivalent | 42 min
**Scenario.** Dispatch needs proof that a recovery artefact can be retrieved or that an apparent outage has been isolated. Use your assigned lane. **Tools:** lane A browser + PowerShell; B browser + local lab; C local lab and inventory; workbook **2 Evidence**. Keep Terminal 1 and 2 running.
1. Assign an operator, a verifier and an evidence owner (combine roles in a pair). Record your lane and one prediction. **All lanes:** do the gateway fault: `python -m exercises.day07_lab point 8072`. Compare `python -m exercises.day07_lab call health` with `python -m exercises.day07_lab call health --port 8071`. Decide which component to investigate first. Restore `python -m exercises.day07_lab point 8071`; verify via browser. No application or database deletion is needed.
2. **A — approved object round trip.** Trainer must confirm a private general purpose **S3 Standard** training bucket, versioning never enabled, Object Lock off, default SSE-S3, disposal allowed, existing prefix or designated root and cost approval. If any is unknown, take B/C. Run `python -m exercises.day07_lab manifest team-a` using your team label. It prints the exact new file and its SHA-256. Only this small fictional text file may go to AWS.
3. **A continued.** S3 → **General purpose buckets → assigned bucket → Objects → assigned existing prefix → Upload → Add files**. Select the printed file. Leave ACL, storage class and encryption at the approved defaults, then **Upload**. Check success, return to the prefix, select exactly your key, choose **Download**, and locate that new download on your machine. `Get-FileHash -Algorithm SHA256 -LiteralPath (Read-Host 'Full downloaded file path')`. Compare with the original. Select exactly your key → **Delete** → enter the displayed confirmation → **Delete objects**. Refresh that prefix, search your exact name and record absence, time and verifier. If deletion is denied, notify the trainer immediately with the private resource reference. Never empty a bucket.
4. **B — inspector.** EC2 → **Instances → assigned instance → Networking**. Follow its subnet and security-group links under VPC. Record effective default route, inbound source and port, and what that establishes about reachability. EC2 → **instance → Storage → Volume ID**: note AZ, volume type and attachment. If only S3 is readable, inspect assigned bucket **Properties / Permissions**, and **Objects** only if authorised; record Region, versioning and effective access evidence. With only another approved service read, inspect one actual permitted setting in that service plus the local fixture for missing evidence. Do not record identifiers. Apply your gateway fault evidence to one AWS diagnostic you would try.
5. **C — local infrastructure.** Inspect the inventory’s edge and internal routes and its original application inbound rules. Compare two request paths including an internal source. Use the working local service to run the gateway fault above. Generate a team manifest, copy it into a new local folder outside Git, hash the downloaded-equivalent file and compare. Label this a local copy. Explain one thing it cannot establish about IAM. If Docker works, point the gateway at the historical container using the supplementary lab and compare the auth boundary.
6. **Every team:** inspect an authorised existing hosting target if visible (EC2 instance or ECS cluster/service), or use the fixture for an explicitly hypothetical appraisal. Record **Could we deploy today?** Identify image entry point, identity/deploy authority, TLS, network path, database location, monitoring, rollback, cost owner and at least one missing prerequisite. Leave actual deployment for an approved release.
**Done when:** two pieces of real machine evidence support the diagnosis, or cloud and local observations are distinguished; the correct path works again; route A also proves hash equality and verified cleanup or reports the precise unresolved owner action. **Stretch:** justify whether retries would help the observed failure.

## 5 · Recover a booking and measure the loss window | 35 min
**Scenario.** The booking server fails after the last consistent backup. Dispatch needs to know which bookings can be recovered and how long a recovery actually takes. **Tools:** three local terminals, stopwatch, workbook. **Start:** known working gateway targeting 8071, active API using **primary**. Confirm which mode is running.
1. Record clock time, create uniquely labelled booking **A-before** and note its ID. Use `python -m exercises.day07_lab call book --as dispatcher --title "Team A before checkpoint"` in protected mode. In historical mode omit `--as dispatcher`. List rows to prove the write.
2. Create a fresh checkpoint, e.g. `python -m exercises.day07_lab backup checkpoint-a --store primary`. Record the completion time. Create **B-after** with a distinct title, note ID and time, and verify both bookings in primary. On repeats change checkpoint and destination names.
3. Stop **only Terminal 1’s API** with Ctrl+C. Leave the gateway running. On the first failed gateway health probe start your timer and record the observation. Do not destroy the original store.
4. Terminal 3: `python -m exercises.day07_lab restore checkpoint-a --store recovered-a`. Terminal 1: restart `python -m exercises.day07_lab api --mode protected --store recovered-a`, substituting historical only if you used it earlier. Check via the gateway. Stop timing when an appropriate reader can access the restored booking list (visitor only for historical).
5. Run `python -m exercises.day07_lab rows --store recovered-a` and `python -m exercises.day07_lab rows --store primary`. Record exactly which IDs survived on each. State recovery time, age of the checkpoint at failure, lost business event(s), target RPO/RTO and one improvement. A measured time in a local rehearsal is evidence for this run.
6. Team A: what changes if the host and its disk disappear together? B: what if the entire AZ goes away? C: what if load doubles but data must stay consistent? Use evidence to distinguish each proposed remedy.
**Done when:** you have two timed observations, both store comparisons, a peer-verified recovery and one AWS change with a stated limitation. **Stretch:** repeat with a new checkpoint and store name; compare the recovery window.

## 6 · Cost and defend two designs | 33 min
**Scenario.** The Northbridge panel will fund either a small office pilot or a more resilient service for dispatch. Build **both** options and recommend a next step. **Tools:** diagram **Small pilot / Resilient service**, workbook **3 Costs / 4 Panel**, [dated offline price sheet](day07-rates.md) or AWS Pricing Calculator. **Prerequisite:** previous evidence and one observed failure.
1. Spend 17 minutes on both designs. Draw the pilot with a single compute host, entry path, persistent SQLite, encryption and tested backup. Draw a resilient alternative with traffic distribution, application capacity in two AZs, independent data availability, monitoring and a genuine migration if proposing PostgreSQL. Mark callers, ports, route/identity boundaries, and health/readiness. Describe loss/recovery, security, limits and operational ownership for each.
2. Use the same Region, currency and hours for both. The offline rates are for us-east-1, USD, 730 hours. Enter units in **3 Costs**, including an explicit 0 for unused items. Specify instance/task counts, storage GB, snapshots, public IP hours, traffic, logs, DB topology, endpoints and exclusions. Add separately sourced extras to the workbook and record the calculation. Test a doubling assumption. State one monthly total per design.
3. Pitch for two minutes, then take two minutes of questions per team (12 minutes total). Each panel reviewer must challenge an observable assumption. Use remaining four minutes for your verdict and a change prompted by review.
4. Each person records one deploy condition and one infrastructure input to carry into Day 8 Terraform (e.g. approved Region, subnet CIDRs, port, tags, DB decision). Assign owners and checks to the outstanding PR permissions, failed-security-check packaging evidence and independent review.
**Done when:** a second team can reproduce your totals, identify the primary failure in each option and trace a booking securely. Submit both diagrams and your decision. **Stretch:** give the monthly cost and recovery consequence of losing one capacity layer.
